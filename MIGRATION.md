# Migration Guide

This guide covers the upgrade from the protocol-only version of Tools4SwiftData (the `master` branch before the introduction of macros) to the current version. It is a major release: most of the public API changed.

The upgrade has three parts:

1. [Update the toolchain and imports](#1-toolchain-and-imports).
2. [Migrate your models](#2-models), either by adopting `@DataTransferObject` (recommended) or by updating your hand-written conformances.
3. [Update the code that uses the provider and the managers](#3-provider) and [handle the new errors](#5-errors).

Your existing stores keep working: a provider created as described in [section 3](#3-provider) opens the same file as before.

---

## 1. Toolchain and imports

**Swift 6 is required.** The package now uses `swift-tools-version: 6.0` (Xcode 16 or later) and depends on [swift-syntax](https://github.com/swiftlang/swift-syntax) for its macros. watchOS 10 is now supported.

**SwiftData is no longer re-exported.** The previous version declared `@_exported import SwiftData`, so importing Tools4SwiftData was enough. Import SwiftData explicitly in every file that uses its types:

```swift
import SwiftData
import Tools4SwiftData
```

## 2. Models

### What changed in the protocols

| Protocol | Before | Now |
|---|---|---|
| `SwiftDataPersistable` | `static var filePrefix: String` | Removed: the store name is passed to the provider |
| | `associatedtype ConfigurableType` | `associatedtype ConfigurableType` and `associatedtype TransferableType` |
| | `init(_ configurableModel: ConfigurableType)` | `init(_ configurable: ConfigurableType, in context: ModelContext) throws` |
| | `func update(using: ConfigurableType) throws` | `func update(using: ConfigurableType, in context: ModelContext) throws` |
| `SwiftDataConfigurable` | `Sendable` | `Hashable, Sendable` |
| | — | `associatedtype PersistableType`, `associatedtype TransferableType` |
| | — | `var persistentModelID: PersistentIdentifier? { get }` |
| | — | `init(_ transferable: TransferableType)` |
| | `validate(for:)` required | `validate(for:)` optional, accepts everything by default |
| `SwiftDataTransferable` | `Sendable` | `Hashable, Sendable` |
| | `associatedtype PersistableType` | `associatedtype PersistableType` and `associatedtype ConfigurableType` |

The three types of a model now refer to each other: a draft knows its snapshot type and the identifier of the model it was taken from, which is what makes updates of existing models and of relationships possible.

### Option A: adopt `@DataTransferObject` (recommended)

The macro generates the snapshot (`Item.Transferable`), the draft (`Item.Configurable`), both initializers of the model and the `SwiftDataPersistable` conformance.

**Before**

```swift
@Model
final class Item: SwiftDataPersistable {
    static let filePrefix = "Items"

    var name: String
    var quantity: Int

    init(_ configurableModel: ItemDraft) {
        name = configurableModel.name
        quantity = configurableModel.quantity
    }

    func update(using configurable: ItemDraft) throws {
        name = configurable.name
        quantity = configurable.quantity
    }
}

struct ItemDraft: SwiftDataConfigurable {
    var name: String
    var quantity: Int

    func validate(for scope: SwiftDataValidationScope) throws {
        guard !name.isEmpty else { throw ItemError.emptyName }
    }
}

struct ItemDTO: SwiftDataTransferable {
    typealias PersistableType = Item

    let persistentModelID: PersistentIdentifier
    let name: String
    let quantity: Int

    init(_ persistentModel: Item) {
        persistentModelID = persistentModel.persistentModelID
        name = persistentModel.name
        quantity = persistentModel.quantity
    }
}
```

**After**

```swift
import SwiftData
import Tools4SwiftData

@Model @DataTransferObject
final class Item {
    var name: String
    var quantity: Int

    init(name: String, quantity: Int) {
        self.name = name
        self.quantity = quantity
    }
}

extension Item.Configurable {
    func validate(for scope: SwiftDataValidationScope) throws {
        guard !name.isEmpty else { throw ItemError.emptyName }
    }
}
```

Step by step:

1. Add `@DataTransferObject` after `@Model` and remove the explicit `SwiftDataPersistable` conformance.
2. Delete your draft and snapshot types, and the `init(_:)` and `update(using:)` that used them.
3. Keep, or write, an initializer of your own: `@Model` requires one in the class body and cannot see the one generated by the macro.
4. Move `validate(for:)` into an extension of `Item.Configurable`. On a `public` model, declare it `public`.
5. Note the value of `filePrefix` before deleting it: it is the store name you will pass to the provider.
6. Replace the old type names in your code (`ItemDraft` → `Item.Configurable`, `ItemDTO` → `Item.Transferable`). During the transition, type aliases avoid touching every call site at once:

   ```swift
   typealias ItemDraft = Item.Configurable
   typealias ItemDTO = Item.Transferable
   ```

The macro has a few requirements, all reported as compile-time errors when not met:

- Stored properties need an explicit type annotation (`var count: Int = 0`, not `var count = 0`), unless excluded with `@IgnoredByDTO`.
- Excluded properties (`@IgnoredByDTO`, SwiftData's `@Transient`) need a default value.
- Relationships need an explicit `@Relationship` attribute and one of the types `Model`, `Model?`, `[Model]`, `[Model]?`. The related model must use the macro too.
- Every attribute type must be `Hashable` and `Sendable`.

The generated types differ from typical hand-written DTOs in two ways:

- To-one relationships are represented by the related model's `PersistentIdentifier`, not by an embedded snapshot.
- To-many relationships are embedded by value. A many-to-many relationship must exclude one of its sides with `@IgnoredByDTO`.

If you declared your own nested types named `Transferable` or `Configurable` inside the model, rename or remove them: they clash with the generated ones.

See the README for relationships, orphan handling and validation in detail.

### Option B: keep hand-written conformances

Update your types to the requirements in the table above:

```swift
@Model
final class Item: SwiftDataPersistable {
    typealias ConfigurableType = ItemDraft
    typealias TransferableType = ItemDTO

    var name: String

    init(_ configurable: ItemDraft, in context: ModelContext) throws {
        name = configurable.name
    }

    func update(using configurable: ItemDraft, in context: ModelContext) throws {
        name = configurable.name
    }
}

struct ItemDraft: SwiftDataConfigurable {
    typealias PersistableType = Item
    typealias TransferableType = ItemDTO

    private(set) var persistentModelID: PersistentIdentifier?
    var name: String

    init(name: String) {
        self.name = name
    }

    init(_ transferable: ItemDTO) {
        persistentModelID = transferable.persistentModelID
        name = transferable.name
    }
}

struct ItemDTO: SwiftDataTransferable {
    typealias PersistableType = Item
    typealias ConfigurableType = ItemDraft

    let persistentModelID: PersistentIdentifier
    let name: String

    init(_ persistentModel: Item) {
        persistentModelID = persistentModel.persistentModelID
        name = persistentModel.name
    }
}
```

Both value types must now be `Hashable`: the conformance is synthesized when all their properties are. The `ModelContext` passed to the initializer and to `update(using:in:)` lets you resolve related models; `ModelContext.resolveRelationship(_:as:)`, `resolveRequiredRelationship(_:as:)` and `reconcile(_:with:orphans:)` are the helpers the macro uses, and are available to your code as well.

## 3. Provider

`SwiftDataProvider` is no longer generic, and the store name is now explicit.

| Before | Now |
|---|---|
| `SwiftDataProvider<ItemDTO>(writeDataStoreAt: directory)` | `SwiftDataProvider(for: [Item.self], storeName: "Items", in: directory)` |
| `SwiftDataProvider<ItemDTO>(writeDataStoreAt: directory, migrationPlan: Plan.self)` | `SwiftDataProvider(schema: Schema([Item.self]), storeName: "Items", in: directory, migrationPlan: Plan.self)` |
| `provider.managerCreator()` | `provider.createManager(for: Item.self)` or `await provider.createBackgroundManager(for: Item.self)` |

> [!IMPORTANT]
> **Pass the old `filePrefix` as `storeName`.** The previous version stored the data in `<directory>/<filePrefix>.sqlite`; the new one uses `<directory>/<storeName>.sqlite`. With the same directory and name the provider opens your existing store. A different name silently opens a new, empty store.

**One store per provider.** Previously each provider managed exactly one model type, in its own file. To keep your data where it is, keep one provider per existing store:

```swift
let items = try SwiftDataProvider(for: [Item.self], storeName: "Items", in: directory)
let orders = try SwiftDataProvider(for: [Order.self], storeName: "Orders", in: directory)
```

A single provider can now hold several model types, with relationships between them, in one store. Merging existing stores into one is a data migration that this package does not perform: copy the data yourself if you need it.

**Where managers run.** A `SwiftDataManager` works on the thread it was created on. `createManager(for:)` behaves like `managerCreator()` did; `createBackgroundManager(for:)` creates the manager off the main thread and is the right choice when the caller is on the main actor.

`SwiftDataProvider(container:)` and `SwiftDataProvider.inMemory(for:)` are new, for custom container configurations and for tests and previews.

## 4. Manager

`SwiftDataManager` is now generic over the model, not over the snapshot type: `SwiftDataManager<ItemDTO>` becomes `SwiftDataManager<Item>`.

| Before | Now |
|---|---|
| `fetch()` | `fetch()` |
| — | `fetch(_ descriptor: FetchDescriptor<Item>)` |
| `fetch(id:)` | `fetch(id:)`, now `throws` |
| `addItem(_:skipValidation:) -> Transferable` | `insert(_:skipValidation:) -> Transferable` |
| `addItem(_:skipValidation:) -> PersistentIdentifier` | `insert(_:skipValidation:).persistentModelID` |
| `updateItem(id:configurable:)` | `update(id:with:)` |
| `updateItem(id:handler:)` | `update(id:handler:)`, the handler can now throw |
| `deleteItem(id:ignoreNonExistent:)` | `delete(id:ignoreNonExistent:)` |

Behavior changes worth knowing:

- **Failed writes are rolled back.** Previously a failure (a throwing `update(using:)`, a failed save) left pending changes in the manager's context, and the next successful save persisted them. Now every write is either saved or rolled back.
- **Snapshots are taken after the save**, so `insert` returns the permanent identifier of the new model.
- **`update(id:with:)` checks the draft's identifier**: a draft taken from a different model is rejected with `identifierMismatch`.
- **Nested drafts are validated.** With the macro, the drafts of to-many relationships are validated too; `skipValidation` only skips the top-level draft.

## 5. Errors

`Tools4SwiftData.internalError` is replaced by `Tools4SwiftDataError`, whose cases say what went wrong:

| Case | Thrown when |
|---|---|
| `.notFound(PersistentIdentifier)` | The model to update or delete does not exist (previously `internalError`) |
| `.identifierMismatch(expected:found:)` | A draft is applied to a model other than its own |
| `.missingIdentifier` | `ManagedQuery`'s `commit(draft:)` receives a draft without identifier |
| `.missingRelationship` | A required to-one relationship has no identifier in the draft |
| `.unresolvedRelationship(PersistentIdentifier)` | A relationship identifier does not match any model |

Update the code that catches the old error:

```swift
// Before
catch Tools4SwiftData.internalError { ... }

// Now
catch Tools4SwiftDataError.notFound(let id) { ... }
```

The old enum also shadowed the module name, so `Tools4SwiftData.SomeType` could not be written in client code; with the rename, module-qualified names work.

## 6. New in this version

These additions need no migration but are worth a look in the README:

- `@DataTransferObject` and `@IgnoredByDTO`, with compile-time diagnostics.
- Relationship support: to-one relationships resolved by identifier, to-many relationships reconciled in place, with a configurable orphan policy (`@DataTransferObject(orphans: .delete)`).
- `ManagedQuery` and `QueryResult`, a SwiftUI layer that keeps a list of snapshots with editable drafts in sync with the store.
- Fetching with a `FetchDescriptor`.

## Checklist

- [ ] Xcode 16 or later; `import SwiftData` added where SwiftData types are used.
- [ ] Each model adopts `@DataTransferObject` (with an initializer of its own and explicit `@Relationship` attributes) or has updated hand-written conformances.
- [ ] Validation moved to `extension Item.Configurable` (when adopting the macro).
- [ ] Every provider created with the old `filePrefix` as `storeName`, one provider per existing store.
- [ ] `managerCreator()` replaced by `createManager(for:)` or `createBackgroundManager(for:)`.
- [ ] `SwiftDataManager<ItemDTO>` replaced by `SwiftDataManager<Item>`, and `addItem`/`updateItem`/`deleteItem` by `insert`/`update`/`delete`.
- [ ] Code catching `Tools4SwiftData.internalError` updated to `Tools4SwiftDataError`.
